Example: Receives requests from Docker Client and executes them.

→ Blueprint used to create Docker images.
Example:
FROM nginx
COPY . /usr/share/nginx/html

Build
→ Converts Dockerfile into Docker Image.
Example:
docker build -t myapp:v1 .

-t = tag (assigns image name and version)
myapp = image name
v1 = image version
. = current directory containing Dockerfile

→ Read-only application package containing code, libraries, runtime, dependencies.

docker images

Registry
→ Storage location for Docker images.
Example:
Docker Hub, ACR, ECR, Harbor

Docker Hub
→ Default public Docker registry.
Example:
docker pull nginx

Container
→ Running instance of an image.
Example:
docker run nginx

containerd
→ Handles container lifecycle operations.
Example:
Create, start, stop, delete containers.

runc
→ Low-level runtime responsible for actually creating containers.

Namespaces
→ Provides isolation between containers.

PID Namespace

cgroups
→ Controls resource limits.
Examples:
CPU Limit

Volume
→ Persistent storage independent of container lifecycle.

Linux Kernel
→ Provides namespaces, cgroups, networking and filesystem support for containers.

A Docker container is not a VM. At the kernel level, it is just a normal Linux process. Docker uses namespaces to make that process appear isolated, cgroups to control resources, OverlayFS to build the container filesystem from image layers, and containerd/runc to communicate with the Linux kernel and start the process.


=============Containers lifecycle========================
Dockerfile
    ↓
A Dockerfile is a blueprint for the application.
It contains instructions such as the base image,
dependencies, files to copy, environment variables,
and the command to start the application.

    ↓

Build
    ↓
Docker reads the Dockerfile and executes each
instruction step by step. Each instruction creates
an image layer and finally produces a Docker image.
Example: docker build -t myapp .

    ↓

Image
    ↓
A Docker image is a read-only, immutable package
containing application code, runtime, libraries,
dependencies, and configuration. It serves as a
template for creating containers.

    ↓

Create
    ↓
Docker creates a container from the image.
A writable layer is added on top of the image,
container metadata is generated, networking is
configured, and resources are allocated.
The container exists but is not yet running.

    ↓

Start
    ↓
Docker starts the container and launches the
main application process (PID 1). Namespaces,
cgroups, networking, and storage are attached
to make the container operational.

    ↓

Running
    ↓
The application is actively executing. It can
accept requests, process data, communicate over
the network, write logs, and consume CPU and
memory resources. The container remains alive
as long as PID 1 is running.

    ↓

Pause / Unpause (Optional)
    ↓
Pause temporarily freezes all processes inside
the container without stopping it. Memory and
networking remain intact. Unpause resumes
execution from the exact point where it stopped.

    ↓

Stop
    ↓
Docker gracefully stops the container by sending
SIGTERM to the main process. This allows the
application to finish ongoing work and release
resources. If it does not stop within the timeout,
Docker sends SIGKILL.

    ↓

Exited
    ↓
The container is no longer running because the
main application process has terminated. The
container still exists along with its logs,
configuration, and metadata, and can be restarted.

    ↓

Remove
    ↓
Docker permanently deletes the container,
including its writable layer, metadata, and logs.
The underlying Docker image remains available and
can be used to create new containers later.

Step 1: What Docker Really Is

Many people think Docker is a virtual machine. It is not.

Docker is essentially:

Application Packaging + Process Isolation


Docker runs applications as isolated processes on the host OS.

When you start a container:

docker run nginx


Docker is simply creating a Linux process and applying isolation mechanisms around it.

Step 2: Traditional Linux Process

Suppose you run:

java app.jar


Linux creates a process.

Host OS
 ├── Process 1 (Systemd)
 ├── Process 2 (Nginx)
 ├── Process 3 (Java App)
 └── Process 4 (Mysql)


All processes can potentially see the same OS environment.

No strong isolation.

Step 3: Docker Creates Isolated Processes

When Docker starts a container:

docker run myapp


Linux still creates a process.

However Docker tells Linux:

Create a process
+
Isolate it
+
Limit resources
+
Give it its own network
+
Give it its own filesystem


Result:

Host OS

Container A
 └── Java App

Container B
 └── Node App

Container C
 └── Python App


Each container thinks:

"I am the only system running"


even though they share the same kernel.

Step 4: Linux Namespaces (Core Isolation Technology)

Namespaces provide isolation.

Think of namespaces as giving every container its own "view" of the system.

Without namespaces:

All applications
  ↓
See same processes
See same hostname
See same network


With namespaces:

Container A
  └─ Own View

Container B
  └─ Own View

PID Namespace

PID = Process ID.

Normal Linux:

ps -ef


May show:

PID 1  systemd
PID 2  nginx
PID 3  mysql
PID 4  java


Inside a container:

ps -ef


You might see:

PID 1 java


Container believes:

I own PID 1


Reality:

Host PID = 3546


Linux hides the real PID using namespace isolation.

Network Namespace

Each container gets:

Own IP
Own routing table
Own ports
Own network interfaces


Container A:

172.17.0.2


Container B:

172.17.0.3


Container thinks:

This is my network


but Docker bridges them through virtual networking.

Mount Namespace

Provides filesystem isolation.

Container sees:

/
├── app
├── logs
└── config


while host sees:

/
├── home
├── usr
├── var
└── opt


Different filesystem views.

Hostname Namespace

Container can have:

hostname


Output:

user-service


Another container:

product-service


Each thinks it has its own machine identity.

User Namespace

Maps container users to host users.

Example:

Container Root User
        ↓
Host User 1001


Provides additional security.

Step 5: cgroups (Control Groups)

Namespaces isolate.

cgroups control resources.

Without cgroups:

Container A
Consumes all RAM
Consumes all CPU


Other applications starve.

Linux cgroups prevent that.

Example

Run container:

docker run --memory=2g --cpus=2 myapp


Linux creates restrictions:

Memory = 2GB
CPU = 2 cores


Container cannot exceed those limits.

Imagine a Hotel

Namespaces:

Give each guest their own room.


cgroups:

Limit how much electricity and water they can use.


Together:

Isolation + Resource Control


which is exactly what containers need.

This is called the Union File System.

Complete Interview Answer

Docker is a containerization platform that runs applications as isolated Linux processes rather than virtual machines. Unlike VMs, containers share the host OS kernel and therefore do not require a separate guest operating system. Docker relies on Linux namespaces for isolation of processes, networking, filesystems, and hostnames, while cgroups enforce CPU, memory, and I/O limits. Docker images are built using layered filesystems and a Union File System, making them lightweight and efficient. When a container starts, Docker uses containerd and runc to create namespaces, apply cgroups, attach networking, and launch the application process. This makes containers fast, portable, resource-efficient, and highly suited for microservice architectures where each service can run independently in its own container.
